# Бенчмарки AMDB

Набор соответствует §7.2 техпроекта. Все числа воспроизводимы: фиксированный
seed, `min` по нескольким прогонам, прогрев перед замером.

| Скрипт | Бенчмарки | Что показывает |
|---|---|---|
| `bench_convolve.py` | B1, B2 | Воспроизведение таблицы 1 статьи Симакова; масштабирование по рангу |
| `bench_olap.py` | B3, B4, B5 | Критерий приёмки ТЗ; сравнение с DuckDB/pandas; плотное против разреженного |
| `bench_gpu.py` | B6 | CPU против CUDA с учётом переноса данных (пропускается без GPU) |
| `bench_duckdb.py` | B7 | Отдельный стенд: одна база, 11 запросов, сверка результатов с DuckDB |
| `bench_scaling.py` | B8 | Развёртки по объёму фактов, размеру куба и перекосу — граница применимости |
| `bench_materialized.py` | B9 | Симметричное сравнение: обе системы стартуют из предпосчитанной сводки |
| `bench_split.py` | B10 | Цена разбиения работы по скоттовой оси против свободной |

```bash
python bench/bench_convolve.py
```

```bash
python bench/bench_olap.py --rows 500000
```

```bash
python bench/bench_gpu.py
```

```bash
python bench/bench_duckdb.py --rows 500000
```

```bash
python bench/bench_scaling.py
```

Сравнение с сырыми фактами асимметрично: у AMDB сводка предпосчитана, у DuckDB
нет. `bench_materialized.py` выдаёт DuckDB таблицу той же гранулярности, что и
гиперкуб (факт, свёрнутый до ключа куба, плюс счётчик строк), и тем отделяет
вклад предварительной агрегации от вклада матричного исполнения.

```bash
python bench/bench_materialized.py --rows 2000000
```

`bench_split.py` проверяет правило выбора оси дробления: измеряет объём
пересылок и время подготовки полезных нагрузок узлов при разбиении по скоттовой
и по свободным осям.

```bash
python bench/bench_split.py --nodes 4
```

## Результаты на машине разработчика

AMD Ryzen 7 PRO 3700 (8 ядер, 16 потоков), Windows 11, Python 3.12,
NumPy 2.1.1, scipy-openblas 0.3.27, DuckDB 1.5.5.

Это тот же процессор, что и в статье Симакова, — сверка с её таблицей 1
методически корректна.

### B1 — таблица 1 статьи, (1,1)-свёрнутое произведение

| Размер | AMDB (einsum) | Статья: NumPy | Статья: Go посл. | Ускорение над Go |
|---|---:|---:|---:|---:|
| 2D 10×10 | 6.5 мкс | 4.5 мкс | 1.7 мкс | 0.3× |
| 2D 100×100 | 108 мкс | 18 мкс | 139 мкс | 1.3× |
| 3D 10×10×10 | 45.8 мкс | 20.6 мкс | 554 мкс | 12.1× |
| **3D 100×100×100** | **60.5 мс** | 65.1 мс | 5 358 мс | **88.6×** |

Ключевой результат статьи воспроизводится: на 3D 100³ einsum опережает
последовательную реализацию на Go в ~89 раз (в статье — 82×), и время
совпадает с опубликованным NumPy-замером в пределах 8 %.

На малых операндах einsum проигрывает: у него постоянные накладные расходы на
разбор спецификации (~30 мкс), которые окупаются только с ростом объёма.

### B3 — критерий приёмки ТЗ (500 000 строк, гиперкуб 100×100×100)

Загрузка в гиперкуб: 462 мс, заполненность 39 %, 7.6 МиБ.

| Запрос | Трансляция | Вычисление | Строк | einsum |
|---|---:|---:|---:|---|
| Агрегация по 1 измерению | 0.02 мс | 0.71 мс | 100 | `abc->a` |
| JOIN + ROLLUP, 2 измерения | 0.03 мс | 11.8 мс | 1 200 | `abc,b,cd->ad` |
| То же с фильтром | 0.02 мс | 1.53 мс | 600 | `abc,b,cd,c->ad` |
| Агрегация по 3 измерениям | 0.08 мс | 76.9 мс | 393 325 | `abc->abc` |

**Требование ТЗ «< 1 с» выполнено с запасом от 13 до 1700 раз.**

### B4 / B7 — сравнение с колоночной СУБД DuckDB

Отдельный стенд `bench_duckdb.py`: строит звёздную схему, загружает её в обе
системы, прогоняет 11 запросов и **сверяет результаты**. Расхождение считается
провалом запроса: быстрый неправильный ответ ничего не стоит.

500 тыс. строк фактов, гиперкуб 100×100×100, выдача в виде кадра данных:

| Запрос | AMDB | DuckDB 1.5.5 | Отношение | Окупаемость |
|---|---:|---:|---:|---:|
| Q1. Скалярная сумма | 0.41 мс | 1.00 мс | 2.5× | 774 зпр |
| Q2. Группировка по 1 измерению | 2.01 мс | 4.96 мс | 2.5× | 157 зпр |
| Q3. Соединение со справочником | 1.66 мс | 7.53 мс | 4.5× | 79 зпр |
| Q4. Соединение и свёртка по иерархии | 1.29 мс | 11.62 мс | **9.0×** | 45 зпр |
| Q5. То же с фильтром | 1.28 мс | 8.98 мс | 7.0× | 60 зпр |
| Q6. Диапазонный фильтр | 1.20 мс | 5.29 мс | 4.4× | 113 зпр |
| Q7. COUNT по месяцам | 0.80 мс | 6.52 мс | 8.1× | 81 зпр |
| Q8. AVG по кварталам | 1.46 мс | 6.30 мс | 4.3× | 96 зпр |
| Q9. Умеренно широкий результат | 1.47 мс | 7.27 мс | 4.9× | 80 зпр |
| Q10. Широкий результат (394 тыс. строк) | 27.79 мс | 37.96 мс | 1.4× | 46 зпр |
| Q11. COUNT DISTINCT | 6.55 мс | 9.52 мс | 1.5× | 156 зпр |

Все 11 результатов совпали с DuckDB. Построение гиперкуба — 462 мс однократно;
столбец окупаемости показывает, со скольких запросов к одному набору данных
подход себя оправдывает.

**Главная закономерность:** преимущество падает с ростом выдачи — 9.0× при
1200 строках против 1.4× при 394 тысячах. Свёртка дешевеет с каждым свёрнутым
измерением, а сборка результата — нет.

**Формат выдачи решает исход.** Флаг `--fetch` переключает между кадром данных
и кортежами Python, и на широком запросе разница принципиальна:

| Выдача 394 тыс. строк | AMDB | DuckDB |
|---|---:|---:|
| Кадр данных (`to_pandas` / `fetchdf`) | 27.6 мс | 39.8 мс |
| Кортежи Python (`.rows` / `fetchall`) | 73.3 мс | 191.2 мс |

До оптимизации результата `to_pandas()` занимал 238 мс — кадр собирался из
кортежей. Теперь результат хранится по столбцам, а строки материализуются
лениво.

**Оговорка о корректности сравнения.** DuckDB работает по сырым таблицам и при
каждом запросе выполняет соединение заново, AMDB пользуется заранее
построенным гиперкубом. Сравнение отвечает на вопрос «что выгоднее при
повторных запросах к неизменному набору», а не «что быстрее вообще».

Корректность трансляции проверяется тем же набором запросов в
`tests/test_duckdb_parity.py`, где DuckDB выступает оракулом.

### B8 — развёртки: где проходит граница применимости

Одна точка замера говорит мало. `bench_scaling.py` меняет три параметра.

**Объём фактов при неизменном кубе 100×100×100.** Преимущество **растёт**:
куб не меняется в размере, а DuckDB обрабатывает всё больше строк.

| Строк | Заполн. | Загрузка | Свёртка 2 осей | Соединение+иерархия | Широкая выдача |
|---:|---:|---:|---:|---:|---:|
| 100 тыс. | 9.5 % | 101 мс | 1.7× | 7.6× | 1.3× |
| 500 тыс. | 39.4 % | 465 мс | 2.5× | 9.0× | 1.4× |
| 2 млн | 86.5 % | 1 903 мс | 5.2× | 19.8× | 1.7× |
| 5 млн | 99.3 % | 4 667 мс | **7.5×** | **33.2×** | 2.6× |

**Размер куба при неизменных 2 млн фактов.** Здесь проходит граница:

| Куб | Ячеек | Заполн. | Память | Свёртка 2 осей | Соединение+иерархия | Широкая выдача |
|---|---:|---:|---:|---:|---:|---:|
| 50³ | 125 тыс. | 100 % | 2 МиБ | 29.4× | 52.3× | 5.7× |
| 100³ | 1 млн | 86.5 % | 15 МиБ | 5.1× | 19.8× | 1.8× |
| 150³ | 3.4 млн | 44.7 % | 51 МиБ | 1.3× | 6.6× | 1.2× |
| 200³ | 8 млн | 22.1 % | 122 МиБ | **0.53×** | 3.2× | 0.94× |

**Перекос распределения при неизменных куба и числе фактов.** Не меняет ничего:

| Перекос | Заполн. | Свёртка 2 осей | Соединение+иерархия | Широкая выдача |
|---:|---:|---:|---:|---:|
| 0.0 | 39.4 % | 1.10× | 6.08× | 1.12× |
| 0.6 | 30.7 % | 1.07× | 5.27× | 1.18× |
| 1.0 | 17.1 % | 1.10× | 5.50× | 1.15× |
| 1.4 | 7.2 % | 1.09× | 5.16× | 1.07× |

**Правило, вытекающее из трёх развёрток.** Время свёртки определяется **числом
ячеек** и не зависит ни от числа фактов, ни от их распределения; время
колоночной СУБД — **числом строк**. Значит отношение времён есть функция
одной величины — числа фактов на ячейку. Проверка: 3.4 млн ячеек при 2 млн
фактов (0.59 факта/ячейку) дают 1.33×, а 4 млн ячеек при тех же фактах
(0.5 факта/ячейку) — 1.10×; точки из разных развёрток совпадают.

**Критерий применимости:** подход выгоден, пока на ячейку приходится порядка
одного факта и более. При 0.25 факта/ячейку простая агрегация уже вдвое
медленнее, чем в DuckDB.

### B5 — плотное против разреженного (гиперкуб 10⁶ ячеек)

| Заполненность | Представление | Память, МиБ | Загрузка, мс | Запрос, мс |
|---:|---|---:|---:|---:|
| 39.3 % | dense | 7.63 | 460 | 0.79 |
| 39.3 % | sparse_coo | 12.00 | 612 | 8.56 |
| 11.8 % | dense | 7.63 | 123 | 0.71 |
| 11.8 % | sparse_coo | 3.59 | 149 | 4.45 |
| 2.5 % | dense | 7.63 | 30 | 0.63 |
| 2.5 % | sparse_coo | 0.75 | 30 | 4.06 |
| 0.5 % | dense | 7.63 | 12 | 0.67 |
| 0.5 % | sparse_coo | 0.15 | 7 | 5.14 |

Разреженное представление выигрывает по памяти (при 0.5 % — в 50 раз), но
**проигрывает по времени запроса на всех уровнях разреженности**: einsum
работает только с плотными массивами, и разреженный путь идёт через
собственное хеш-соединение вместо BLAS. Поэтому `DENSE_THRESHOLD` в
`amdb/storage/policy.py` намеренно низкий: разреженное хранение включается
тогда, когда плотное уже не помещается в память, а не «для скорости».
