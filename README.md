# AMDB — алгебраическая машина баз данных

СУБД для OLAP-аналитики на **алгебре многомерных матриц Н.П. Соколова**.
SQL-подобные запросы транслируются в цепочки **(λ, μ)-свёрнутых произведений** и
исполняются одним вызовом `numpy.einsum` поверх оптимизированного BLAS.

Реализация технического проекта [«ПАК Алгебраическая машина баз данных»](docs/Технический%20проект%20AMDB.md).
Как этим пользоваться — [Руководство пользователя](docs/Руководство%20пользователя.md).
Математика — [описание составляющей](docs/Математическая%20составляющая.md) и
[обоснование с доказательствами](docs/Математическое%20обоснование.md).
Насколько реализация соответствует теории — два аудита:
[алгебре Соколова](docs/Соответствие%20теории%20Соколова.md) и
[концепции алгебраической машины](docs/Соответствие%20концепции%20алгебраической%20машины.md).

```sql
SELECT customer, month, SUM(quantity * price) AS revenue
FROM sales JOIN product ON sales.product = product.product
WHERE region = 'Смоленск'
GROUP BY customer, month
```

транслируется в

```python
np.einsum('abc,b,cd,a->ad', sales, price, date_to_month, region_mask)
```

— соединение, фильтрация, свёртка по иерархии и агрегация выполняются **одной
операцией**, а не четырьмя проходами по данным.

## Установка

```bash
pip install -e ".[dev]"
```

Устанавливать не обязательно: скрипты в `examples/` и `bench/`, а также
`python -m amdb`, работают прямо из копии репозитория. Установка нужна лишь
для короткой команды `amdb` и для импорта пакета из чужих проектов.

Обязательна только `numpy`. `pandas` нужна для загрузки таблиц, `h5py` — для
хранения на диске, `fastapi` — для REST, `torch` — для GPU, `chdb` — для
сравнения с ClickHouse.

**Версии имеют значение.** Производительность `einsum` на свёртках со
скоттовыми индексами заметно менялась между выпусками NumPy: на 2.1.1 единый
вызов уступал разложению на сечения восьмикратно, на 2.5.2 разрыв исчез.
Поэтому опубликованные замеры сняты на закреплённом наборе версий:

```bash
pip install -e ".[pinned]"
```

## Быстрый старт

```bash
python examples/generate.py --out data --rows 500000
```

```bash
python examples/demo.py --data data
```

```python
import pandas as pd
from amdb import Database

db = Database()
db.load_csv("data/sales.csv", ["customer", "product", "date"], "quantity", "sales")
db.load_dimension(pd.read_csv("data/products.csv"), "product",
                  attributes=["category"], measures=["price"])
db.add_hierarchy("date", "month", {d: f"M{d // 30 + 1}" for d in range(100)})

print(db.sql("""
    SELECT customer, month, SUM(quantity * price) AS revenue
    FROM sales JOIN product ON sales.product = product.product
    GROUP BY customer, month
    ORDER BY revenue DESC LIMIT 5
""").to_text())
```

Из командной строки:

```bash
python -m amdb --db mybase query "SELECT customer, SUM(quantity) FROM sales GROUP BY customer" --timing
```

```bash
python -m amdb --db mybase explain "SELECT month, SUM(quantity) FROM sales GROUP BY month"
```

```bash
python -m amdb --db mybase shell
```

## Как это работает

Роль индекса в свёртке определяется его ролью в SQL — в этом вся трансляция:

| Роль индекса | Условие | SQL-смысл |
|---|---|---|
| **λ** (сохраняется) | ось общая для операндов и есть в `GROUP BY` | `JOIN` с ключом в группировке |
| **μ** (свёртывается) | ось общая, но в `GROUP BY` её нет | `JOIN` + агрегация по ключу |
| свободная | ось только у одного операнда | измерение одного факта |

Всё остальное — следствия:

* **`WHERE`** становится 0/1-маской и добавляется операндом в ту же свёртку.
  Фильтр не проход по данным, а сомножитель.
* **Иерархии** (`date → month → quarter`) хранятся как разреженные матрицы
  перехода, поэтому `ROLLUP` — обычная (0,1)-свёртка.
* **Оконные функции** — умножение на треугольную (или ленточную) матрицу.
* **Права доступа** — ещё одна маска в той же свёртке: запрещённые данные не
  участвуют в арифметике, а не отфильтровываются после.

```bash
python -m amdb --db mybase explain "SELECT customer, month, SUM(quantity * price) FROM sales JOIN product ON sales.product = product.product WHERE region = 'Смоленск' GROUP BY customer, month"
```

```
  revenue: SUM
      +1 × einsum('abc,b,cd,a->ad')  (1,2)-свёртка
           [sales[customer, product, date], price[product],
            rollup:date->month[date, month], mask:customer[customer]]
```

## Границы применимости (важно)

Проект честно очерчивает, где матричная модель **не** выигрывает:

1. **Гранулярность MIN/MAX.** Гиперкуб хранит агрегат по ячейке, поэтому
   `MAX(quantity)` возвращает максимум **по ячейкам куба**, а не по исходным
   строкам. Если нужен построчный максимум, грузите факт с `agg="max"`.
2. **`COUNT(DISTINCT ...)` — только по измерению.** Выражается композицией
   ∨-свёртки над булевым полукольцом и подсчёта. `DISTINCT` по произвольной
   мере потребовал бы вынести область её значений в отдельную ось и отклоняется.
3. **MIN/MAX исполняются редукцией, а не einsum.** Алгебраически это то же
   (λ, μ)-произведение, но над полукольцом (max, ·) — см.
   [аудит соответствия](docs/Соответствие%20теории%20Соколова.md), §5.1.
   BLAS работает только с (+, ·), поэтому на практике используется прямая
   редукция. Маска прав доступа для них применяется выборкой, а не умножением
   на ноль (иначе ноль стал бы ложным экстремумом).
4. **Разреженный путь медленнее плотного** (см. [bench/README.md](bench/README.md)):
   einsum работает только с плотными массивами. Разреженное хранение включается,
   когда плотное не помещается в память, а не «для скорости».
5. **Комбинаторный взрыв.** Мощности измерений перемножаются. AMDB — ускоритель
   плотных многомерных агрегатов, а не замена колоночной СУБД общего назначения.

## Производительность

Гиперкуб 100×100×100 из 500 000 строк, AMD Ryzen 8 ядер, Ubuntu 24.04,
NumPy 2.5.2 + OpenBLAS:

| Запрос | AMDB | DuckDB 1.5.5 | Отношение |
|---|---:|---:|---:|
| `GROUP BY customer` | 1.02 мс | 1.37 мс | 1.3× |
| `JOIN` + `ROLLUP`, 2 измерения | 3.09 мс | 8.71 мс | **2.8×** |
| То же с фильтром | 3.20 мс | 6.75 мс | 2.1× |
| `GROUP BY` по 3 измерениям (394 тыс. строк) | 18.3 мс | 35.6 мс | 1.9× |

Все 11 запросов стенда дают результат, совпадающий с DuckDB; обе системы
работают на своих внутренних представлениях (гиперкуб против нативных таблиц).
Выигрыш есть на всех запросах — от 1.3 до 4.5 раза, — и наименьший он там, где
запрос сводится к одной агрегации. Однократная загрузка гиперкуба (159 мс)
окупается с 10–29 запросов, а на одиночной группировке — с 458.

Против ClickHouse (26.7.2 через `chdb`, 5 млн фактов) отношение составляет от
3.6 до 66 раз: на звёздной схеме она уступает и DuckDB, тем сильнее, чем больше
в запросе соединений. Стенд — `bench/bench_clickhouse.py`, нужен Linux.

**Как это масштабируется.** Время свёртки зависит от числа **ячеек** куба, а
не от числа фактов, поэтому преимущество растёт с объёмом данных и падает с
размером куба:

| | 100 тыс. фактов | 500 тыс. | 2 млн | 5 млн |
|---|---:|---:|---:|---:|
| Соединение + свёртка по иерархии | 3.2× | 3.8× | 4.3× | **7.8×** |

Граница применимости: подход выгоден, пока на ячейку приходится порядка одного
факта. При 0.25 факта/ячейку (куб 200³ на 2 млн фактов) он уступает DuckDB и на
простой агрегации (0.36×), и на составном запросе (0.64×). Развёртки — [bench/README.md](bench/README.md), B8.

```bash
python bench/bench_duckdb.py --rows 500000
```

Сравнение с сырыми фактами асимметрично: у AMDB сводка предпосчитана, у DuckDB
нет. Симметричный стенд выдаёт DuckDB таблицу той же гранулярности, что и
гиперкуб, и разделяет вклад предпосчёта и вклад алгебры: на простой группировке
преимущество на простой группировке падает с 2.2 до 1.4 раза, а на соединении
со свёрткой по иерархии остаётся до 4.9 раза.

```bash
python bench/bench_materialized.py --rows 2000000
```

Правило выбора оси дробления (скоттова, а не свободная) проверяется отдельно:

```bash
python bench/bench_split.py --nodes 4
```

Требование ТЗ («типовой OLAP-запрос < 1 с») выполнено с запасом в 13–1700 раз.
(1,1)-свёртка 100×100×100 занимает 3.2 мс — против 65.1 мс, опубликованных в
статье про einsum. Столь большая разница объясняется версией библиотеки: на
NumPy 2.1.1 та же свёртка через `einsum` занимает 59.9 мс (опубликованный
результат воспроизводится), а разложение на сечения даёт 3.0 мс. В NumPy 2.5.2
библиотека нашла тот же путь сама, и разрыв исчез — подробности в
[bench/README.md](bench/README.md), раздел «Зависимость от среды».

Подробности и оговорки — [bench/README.md](bench/README.md).

## Проверка в Linux

Сравнение с ClickHouse требует Linux: официальных сборок под Windows нет, и
встраиваемая сборка `chdb` их не предоставляет. Ниже — как поднять среду, в
которой воспроизводятся все замеры, включая трёхстороннее сравнение
`bench/bench_clickhouse.py`.

Замеры **чувствительны к среде**: версии NumPy и pandas меняют отдельные
отношения времён в разы (см. bench/README.md, раздел «Зависимость от среды»).
Поэтому все числа в статье сняты в одной среде, и её описание — часть замера,
а не примечание к нему.

### Если сеть в WSL работает

```bash
wsl -e bash -lc "python3 -m pip install --user numpy pandas pyarrow duckdb chdb pytest"
```

### Если сети в WSL нет

Так бывает при активном VPN, который перехватывает маршрутизацию гостевой
системы. Тогда колёса скачиваются на хосте и переносятся внутрь. Всё ставится
в отдельный каталог через `--target`, поэтому системный Python не меняется, а
удаляется установка одной командой `rm -rf ~/amdbenv`.

Шаг 1, на хосте — скачать колёса под Linux:

```bash
pip download pip numpy pandas pyarrow duckdb chdb chdb-core pytest --only-binary=:all: --python-version 312 --platform manylinux2014_x86_64 --platform manylinux_2_17_x86_64 --platform manylinux_2_28_x86_64 --platform any -d wheels
```

Шаг 2, в WSL — поставить их, минуя сеть. В Ubuntu 24.04 нет ни `pip`, ни
`ensurepip`, поэтому pip запускается прямо из своего колеса:

```bash
wsl -e bash -lc 'W=/mnt/c/путь/к/wheels; python3 $W/pip-*.whl/pip install --no-index --find-links=$W --target=$HOME/amdbenv numpy pandas pyarrow duckdb chdb pytest'
```

### Запуск

Пакет `amdb` не устанавливается — он берётся из копии репозитория:

```bash
wsl -e bash -lc 'export PYTHONPATH=$HOME/amdbenv:/mnt/e/translator; cd /mnt/e/translator && python3 -m pytest tests -q --ignore=tests/test_scripts.py'
```

```bash
wsl -e bash -lc 'export PYTHONPATH=$HOME/amdbenv:/mnt/e/translator; cd /mnt/e/translator && python3 bench/bench_clickhouse.py --rows 5000000'
```

## Параллельное исполнение

Свёртку можно исполнять по независимым скоттовым сечениям в пуле процессов —
это первое разбиение из схемы Мунермана. Реализация в
[amdb/exec/parallel.py](amdb/exec/parallel.py), стенд:

```bash
python bench/bench_parallel.py
```

Замер показал, что на одном узле это **не окупается**: разбиение по сечениям и
многопоточность BLAS занимают одни и те же ядра и заменяют друг друга. Против
однопоточного BLAS выигрыш до 1.66 раза, против многопоточного — нет нигде.
Подробности — bench/README.md, раздел B13.

## Ускоритель

Прежде запуска стендов — самопроверка окружения. Она не требует ни базы, ни
данных и за несколько секунд говорит, чего не хватает; на арендованной машине
это дешевле, чем выяснять то же самое по сообщениям стендов:

```bash
python -m amdb doctor
```

Проверяется замером, а не наличием пакета: считает ли BLAS в несколько потоков,
видна ли карта, выполняются ли на ней операции (у совсем свежих карт бывает, что
`torch.cuda.is_available()` истинно, а ядер под неё в сборке нет), и во сколько
раз двойная точность медленнее одинарной — от этого зависит, годится ли карта
для расчётов, которых требует модель. Заодно печатается, при каком размере куба
автовыбор движка вообще включит ускоритель.

Стенды `bench/bench_gpu.py` (ядро) и `bench/bench_engines.py` (запросы целиком)
меряют GPU в двух режимах: с переносом операндов при каждом вызове и с кубом,
закреплённым на карте между запросами. Точность задаётся явно — по умолчанию
`float64`, как и во всей системе. Результаты сверяются с CPU.

```bash
pip install -e ".[gpu]"
python bench/bench_gpu.py
python bench/bench_engines.py --rows 5000000
```

Столбцы `AMDB CPU`, `DuckDB` и `ClickHouse` во втором стенде должны совпасть с
выводом `bench_clickhouse.py` на той же машине — это точка сверки, по которой
видно, что числа с ускорителем сопоставимы с уже снятыми.

Без CUDA оба стенда отрабатывают, сообщая, чего не хватает.

Тесты из `tests/test_scripts.py` в такой раскладке падают, и это ожидаемо: они
запускают дочерние процессы с намеренно очищенным `PYTHONPATH`, проверяя, что
скрипты работают у того, кто установил пакет через `pip`. При запуске по
`PYTHONPATH` пакет им не виден.

Проверить, что среда собрана верно:

```bash
wsl -e bash -lc 'export PYTHONPATH=$HOME/amdbenv; python3 -c "import numpy, duckdb, chdb; print(numpy.__version__, duckdb.__version__); print(chdb.query(\"SELECT version()\", \"CSV\"))"'
```

## Тесты

```bash
python -m pytest tests -q
```

242 теста. Из них 76 — проверка теоретического соответствия: 52 на алгебру
Соколова (арифметика рангов, билинейность, ассоциативность, транспонирование,
единица, вырождение в частные случаи, область определения полуколец,
инвариантность порядка свёрток на разреженном пути) и 24 на
свойства алгебраической машины (план как терм, инвариантность результата ко
всем 18 порядкам свёрток, интерпретация терма, права доступа как операция,
условие изоморфизма реляционной и матричной моделей).
Каждая аксиома системы **доказана** в
[математическом обосновании](docs/Математическое%20обоснование.md); тесты
проверяют реализацию, а не обосновывают теорию. Остальные тесты: сверка
запросов с pandas как оракулом (относительная погрешность ≤ 1e‑12),
персистентность, CLI.
