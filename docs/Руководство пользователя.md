## 1. Установка

```bash
pip install -e ".[dev]"
```

Устанавливать пакет не обязательно: скрипты в `examples/` и `bench/`, а также
`python -m amdb`, работают прямо из копии репозитория — они сами добавляют её
корень в путь поиска модулей. Установка нужна для короткой команды `amdb`
и для импорта `amdb` из других проектов.

Обязательна только `numpy`. Остальное — по потребности:

| Что нужно | Пакет |
|---|---|
| Загрузка таблиц и `.to_pandas()` | `pandas` |
| Хранение базы на диске в HDF5 | `h5py` (иначе используется `.npz`) |
| REST API | `fastapi`, `uvicorn`, `pydantic` |
| GPU | `torch` |
| PostgreSQL / ClickHouse | `psycopg`, `clickhouse-driver` |

Проверка:

```bash
python -m pytest tests -q
```

## 2. Модель данных: три понятия

AMDB — не реляционная СУБД. Здесь нет таблиц; есть три вещи.

**Измерение** — сущность, задающая одну ось гиперкуба: клиент, товар, дата.
Значения измерения пронумерованы, и номер значения есть индекс вдоль оси.
У измерения могут быть **атрибуты** (`region` у клиента, `category` у товара) —
по ним фильтруют, но не группируют.

**Гиперкуб (куб факта)** — многомерный массив, где по каждой оси стоит
измерение, а в ячейке лежит значение меры. Куб `sales[customer, product, date]`
хранит количество проданного. Куб может быть плотным или разреженным — AMDB
выбирает представление сама.

**Иерархия** — связь «дочернее измерение → родительское»: `date → month →
quarter`, `product → category`. Хранится не деревом, а разреженной матрицей
перехода размера `[child × parent]`. Благодаря этому `GROUP BY month` — не
отдельный код агрегации, а обычное умножение на матрицу.

Реляционная звёздная схема ложится на эту модель почти механически:

| Реляционно | В AMDB |
|---|---|
| Таблица фактов `sales(customer_id, product_id, date_id, quantity)` | Куб `sales[customer, product, date]` с мерой `quantity` |
| Справочник `products(id, category, price)` | Измерение `product` + атрибут `category` + куб `price[product]` |
| Справочник `customers(id, region)` | Измерение `customer` + атрибут `region` |
| Календарь `dates(id, month, quarter)` | Иерархии `date → month → quarter` |

Одно ограничение, которое стоит понять сразу: **ячейка куба хранит агрегат**.
Если две записи имеют одинаковые (клиент, товар, дата), их количества
складываются в одну ячейку. Для `SUM` это ровно то, что нужно; для `MIN`/`MAX`
это меняет смысл (см. §11).

## 3. Первая база за пять минут

Сгенерируем синтетическую звёздную схему:

```bash
python examples/generate.py --out data --rows 500000
```

Получатся четыре CSV: `sales.csv` (500 тыс. строк фактов), `products.csv`,
`customers.csv`, `dates.csv`.

Загрузим факт в гиперкуб:

```bash
python -m amdb --db mybase load data/sales.csv --dimensions customer product date --value quantity --name sales --ordered date
```

```
загружен куб sales: оси ['customer', 'product', 'date'], форма (100, 100, 100),
заполненность 39.361%, представление dense
```

`--ordered date` объявляет измерение упорядоченным — без этого условия вида
`date BETWEEN 10 AND 20` будут отклонены (для числовых измерений порядок
определяется автоматически, флаг нужен для дат-строк и подобного).

Загрузим справочники. Ключевой столбец становится измерением, `--attribute` —
атрибутами для фильтрации, `--measure` — кубами ранга 1:

```bash
python -m amdb --db mybase load data/products.csv --dimension --key product --attribute category --measure price
```

```bash
python -m amdb --db mybase load data/customers.csv --dimension --key customer --attribute region
```

Зарегистрируем иерархию `date → month`:

```bash
python -m amdb --db mybase hierarchy data/dates.csv --child date --parent month --key date --column month
```


## 4. Язык запросов

Диалект близок к SQL, но соединения выполняются по совпадению имён измерений,
а не по произвольным условиям.

```sql
SELECT   <измерения из GROUP BY>, <агрегаты>
FROM     <куб факта>
JOIN     <куб или измерение> [ON a.dim = b.dim]
WHERE    <условия по измерениям и атрибутам>
GROUP BY <измерения>
HAVING   <условия по агрегатам>
ORDER BY <столбец или номер> [ASC|DESC]
LIMIT    <n>
```

### Что поддерживается

| Конструкция | Пример |
|---|---|
| Агрегаты | `SUM(x)`, `COUNT(*)`, `COUNT(x)`, `AVG(x)`, `MIN(x)`, `MAX(x)` |
| Арифметика под агрегатом | `SUM(quantity * price - discount)`, `SUM(quantity / 4)` |
| Арифметика над агрегатами | `SUM(revenue) / SUM(quantity)` |
| Соединение по мере | `SUM(quantity * price)` — меры из разных кубов |
| Сравнения | `=`, `!=`, `<`, `<=`, `>`, `>=` |
| Списки и диапазоны | `product IN (1, 2, 3)`, `date BETWEEN 10 AND 20`, `NOT IN` |
| Логика | `AND`, `OR`, `NOT`, скобки |
| Подзапрос | `customer IN (SELECT customer FROM customers WHERE region = 'Смоленск')` |
| Оконная сумма | `SUM(x) OVER (PARTITION BY c ORDER BY month)` |
| Рамка окна | `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` |
| Кириллица в именах | `SELECT клиент, SUM(количество) FROM продажи GROUP BY клиент` |
| Комментарии | `-- до конца строки` |

Имя, совпадающее с ключевым словом, экранируется двойными кавычками: `"count"`.

### Чего нет

`COUNT(DISTINCT ...)`, `LEFT JOIN` с сохранением несопоставленных строк,
`UNION`, `INSERT`/`UPDATE`/`DELETE`, коррелированные подзапросы, `CASE`,
строковые и датовые функции. Всё это отклоняется с внятным сообщением, а не
считается молча неправильно.

### Примеры

Выручка по клиентам и месяцам:

```sql
SELECT customer, month, SUM(quantity * price) AS revenue
FROM sales JOIN product ON sales.product = product.product
GROUP BY customer, month
```

Средний чек и число сделок по категориям (`category` должна быть заведена как
иерархия `product → category`, иначе группировка по атрибуту не работает):

```sql
SELECT category, COUNT(*) AS deals, AVG(quantity) AS avg_qty
FROM sales GROUP BY category
```

Доля региона: отношение двух агрегатов:

```sql
SELECT customer, SUM(quantity * price) / SUM(quantity) AS avg_price
FROM sales JOIN product ON sales.product = product.product
GROUP BY customer
HAVING avg_price > 500
ORDER BY avg_price DESC
```

Накопительная выручка по месяцам:

```sql
SELECT month, SUM(quantity * price) OVER (ORDER BY month) AS running
FROM sales JOIN product ON sales.product = product.product
GROUP BY month
```

Скользящее окно шириной 3:

```sql
SELECT customer, month,
       SUM(quantity) OVER (PARTITION BY customer ORDER BY month
                           ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3
FROM sales GROUP BY customer, month
```

## 5. Как это работает: от SQL к einsum

### 5.1 Одна идея

В алгебре многомерных матриц Н.П. Соколова есть операция **(λ, μ)-свёрнутого
произведения**:

```
c[l…, s…, m…] = Σ по (c…)  a[l…, s…, c…] · b[s…, c…, m…]
```

Индексы играют три роли: `l`/`m` — свободные (принадлежат только одному
операнду), `s` — общие и **сохраняемые** (их λ штук), `c` — общие и
**свёртываемые**, по ним идёт суммирование (их μ штук).

Ключевое наблюдение, на котором держится весь транслятор:

| Роль индекса | Что это в SQL |
|---|---|
| **λ** — ось общая для операндов и присутствует в `GROUP BY` | `JOIN` по ключу, который остаётся в группировке |
| **μ** — ось общая, но в `GROUP BY` её нет | `JOIN` по ключу + агрегация, «схлопывающая» его |
| свободная — ось есть только у одного операнда | измерение одного факта |

То есть **соединение и агрегация — это одна операция**, а не две. Разница между
ними только в том, попал индекс в `GROUP BY` или нет.

### 5.2 Всё остальное — следствия

**`WHERE` — это операнд, а не проход по данным.** Условие `region = 'Смоленск'`
превращается в 0/1-вектор длины 100 по оси `customer` и добавляется
сомножителем в ту же свёртку. Запрещённые значения умножаются на ноль внутри
той же операции.

**`GROUP BY` по иерархии — это умножение на матрицу.** Иерархия `date → month`
хранится матрицей `[100 × 4]` из нулей и единиц. Свёртка с ней и есть `ROLLUP`.

**Оконная функция — это умножение на треугольную матрицу.** Накопительная сумма
вдоль оси — свёртка с верхнетреугольной матрицей `[from × to]`; скользящее окно
— с ленточной; взвешенное окно — с произвольной. Один механизм на все случаи.

**Права доступа — ещё одна маска.** Роль, которой разрешены не все клиенты,
добавляет в свёртку свой 0/1-вектор. Запрещённые данные не участвуют в
арифметике вовсе, а не отфильтровываются после вычисления.

### 5.3 Посмотреть своими глазами

```bash
python -m amdb --db mybase explain "SELECT customer, month, SUM(quantity * price) AS revenue FROM sales JOIN product ON sales.product = product.product WHERE region = 'Смоленск' GROUP BY customer, month"
```

```
источники: sales, product
GROUP BY: customer, month
фильтр: Mask('customer',) selected=25/100
агрегат: SUM(quantity * price) AS revenue

План выполнения:
  GROUP BY: ['customer', 'month']
  revenue: SUM
      +1 × einsum('abc,b,cd,a->ad')  (1,2)-свёртка
           [sales['customer','product','date'], price['product'],
            rollup:date->month['date','month'], mask:customer['customer']]
  наличие групп: einsum('abc,cd,a->ad')  (1,1)-свёртка
           [sales__count[...], rollup:date->month[...], mask:customer[...]]

Оценки:
  revenue#0: ~1.04e+06 операций, макс. промежуточный 10,000 ячеек
```

Читается так: `abc,b,cd,a->ad` — четыре операнда сворачиваются в один результат
с осями `a` (customer) и `d` (month). Индекс `b` (product) общий для `sales` и
`price` и в выходе отсутствует — это μ. Индекс `c` (date) общий для `sales` и
матрицы перехода — тоже μ. Индекс `a` общий для `sales` и маски и присутствует
в выходе — это λ. Отсюда пометка **(1,2)-свёртка**.

Второй шаг, «наличие групп», нужен для семантики SQL: группа без исходных
записей не должна попадать в результат. Он считает число записей по тем же
маскам и иерархиям, и группы с нулём отбрасываются.

### 5.4 Что происходит по шагам

```
текст запроса
   ↓ лексер + парсер рекурсивного спуска (amdb/ql/lexer.py, parser.py)
AST
   ↓ связывание с каталогом (amdb/ql/binder.py)
   │  имена → измерения и кубы; WHERE → маски; SUM(a*b-c) → сумма произведений
логический запрос
   ↓ планирование (amdb/ql/planner.py)
   │  подбор кубов по мерам, вставка матриц иерархий, вывод ролей λ/μ
физический план: DAG из einsum-шагов
   ↓ оптимизация (amdb/ql/optimizer.py)
   │  порядок свёрток (einsum_path), оценка памяти, декомпозиция при > 52 индексов
   ↓ права доступа (amdb/security/rls.py) — добавление масок роли
   ↓ исполнение (amdb/exec/executor.py)
   │  np.einsum поверх BLAS, либо разреженный путь, либо GPU
таблица результата
```

Скомпилированный план кэшируется по тексту запроса и версиям кубов, поэтому
повторный запрос не проходит трансляцию заново.

## 6. Командная строка

```bash
python -m amdb --db <каталог> <команда> [параметры]
```

После `pip install -e .` доступна короткая форма `amdb --db ... <команда>`.

| Команда | Назначение |
|---|---|
| `load` | Загрузить CSV в куб факта или в справочник (`--dimension`) |
| `hierarchy` | Зарегистрировать иерархию измерений |
| `query` | Выполнить запрос (`--format text\|csv\|json`, `--timing`, `--limit`) |
| `explain` | Показать план: цепочку свёрток с ролями индексов |
| `sokolov` | Разложить план в бинарные (λ, μ)-произведения Соколова |
| `signature` | Сигнатура алгебраической системы: сорта, операции, аксиомы |
| `info` | Измерения, кубы, заполненность, сборка BLAS, наличие GPU |
| `shell` | Интерактивный режим |

В интерактивном режиме: `\e ЗАПРОС` — план, `\s ЗАПРОС` — разложение по
Соколову, `\i` — сведения, `\q` — выход.

```bash
python -m amdb --db mybase shell
```

Вывод в CSV или JSON пригоден для конвейеров:

```bash
python -m amdb --db mybase query "SELECT customer, SUM(quantity) AS q FROM sales GROUP BY customer" --format csv > out.csv
```

Коды возврата: `0` — успех, `2` — ошибка синтаксиса, связывания или доступа,
`3` — ошибка данных или нехватка памяти.

## 7. Python API

```python
import pandas as pd
from amdb import Database

db = Database()

# Факт: три измерения + мера
db.load_csv("data/sales.csv", ["customer", "product", "date"], "quantity",
            name="sales", ordered_dims=["date"])

# Справочник: ключ -> измерение, атрибуты для фильтров, меры -> кубы ранга 1
db.load_dimension(pd.read_csv("data/products.csv"), "product",
                  attributes=["category"], measures=["price"])

# Иерархия: словарь {значение_child: значение_parent}
db.add_hierarchy("date", "month", {d: f"M{d // 30 + 1}" for d in range(100)})

result = db.sql("""
    SELECT customer, month, SUM(quantity * price) AS revenue
    FROM sales JOIN product ON sales.product = product.product
    GROUP BY customer, month
""")

print(result.to_text())          # выравненная таблица
result.to_pandas()               # DataFrame
result.to_dicts()                # список словарей
result.column("revenue")         # один столбец
result.stats                     # время трансляции и вычисления, движок
```

Сохранение и открытие:

```python
db.save("mybase")                # SQLite с метаданными + HDF5/NPZ с массивами
db = Database.open("mybase")
```

Загрузка прямо из СУБД:

```python
import psycopg
with psycopg.connect("postgresql://...") as con:
    db.load_sql(con, "SELECT customer_id, product_id, date_id, qty FROM sales",
                ["customer_id", "product_id", "date_id"], "qty", name="sales")
```

Работа с ядром напрямую, без языка запросов:

```python
from amdb import MultidimensionalMatrix, convolve, convolve_named, build_einsum

build_einsum(6, 9, lam=2, mu=3)          # 'abcdef,bcdefghij->abcghij'
convolve(A, B, lam=1, mu=1)              # свёртка по канонической раскладке осей

a = MultidimensionalMatrix(sales, ("customer", "product", "date"))
b = MultidimensionalMatrix(price, ("product",))
convolve_named(a, b, keep={"product"})   # роли λ/μ выводятся из имён осей
```

Полезная интроспекция:

```python
db.explain(sql)          # план текстом
db.sokolov(sql)          # разложение в бинарные (λ, μ)-произведения
db.term(sql)             # запрос как терм алгебры
db.einsum_of(sql)        # только einsum-строки: ['abc,b,cd->ad']
db.stats("sales")        # nnz, заполненность, память, рекомендуемое представление
db.summary()             # то же, что CLI info
```

## 9. Разграничение доступа

Роль получает права на измерения. Можно ограничить набор видимых значений и
запретить агрегацию по оси (то есть потребовать, чтобы ось была в `GROUP BY`).

```python
smolensk = [c for c, r in zip(db.dimensions["customer"].labels(),
                              db.dimensions["customer"].attributes["region"])
            if r == "Смоленск"]

db.grant("analyst", "customer", allowed=smolensk)   # видит только своих клиентов
db.grant("analyst", "product", can_project=False)   # обязан группировать по товару

db.sql("SELECT customer, SUM(quantity) FROM sales GROUP BY customer", role="analyst")
```

Роль `permissive=True` (по умолчанию) имеет полный доступ к измерениям без
явного гранта; `permissive=False` — только к перечисленным.

Права применяются **внутри свёртки**: маска роли становится ещё одним операндом
einsum. Итоги, посчитанные под ролью, не включают запрещённые данные ни на
каком промежуточном шаге.

Исключение, о котором нужно знать: для `MIN`/`MAX` умножение на ноль дало бы
ложный экстремум, поэтому там права применяются выборкой разрешённых индексов.
Это сделано автоматически.

Для защиты от косвенного раскрытия есть подавление малых ячеек:

```python
from amdb.security import cell_suppression
cell_suppression(values, counts, k=5)   # ячейки менее чем по 5 записям -> NaN
```

## 10. Настройка производительности

**Проверьте BLAS.** `python -m amdb --db ... info` печатает сборку. С эталонной
netlib-BLAS свёртки медленнее на порядок; нужен OpenBLAS или MKL.

**Число потоков** задаётся через BLAS, а не через AMDB:

```bash
OMP_NUM_THREADS=8 python -m amdb --db mybase query "..."
```

**Точность.** По умолчанию `float64` — это осознанный выбор: на `float32`
относительная погрешность суммирования достигает 1e‑7, что неприемлемо для
денежных мер. Если точность не критична, а объём велик:

```python
db.load_csv(..., dtype="float32")   # вдвое меньше памяти, вдвое быстрее свёртка
```

**Представление** выбирается автоматически по заполненности, но его можно
задать явно:

```python
from amdb.storage import DENSE, SPARSE_COO
db.load_csv(..., layout=SPARSE_COO)
```

Важно: разреженное представление экономит память, но **проигрывает плотному по
времени запроса** — einsum работает только с плотными массивами, и разреженный
путь идёт через собственное хеш-соединение вместо BLAS. Включайте его, когда
плотный куб не помещается в память, а не «для скорости». Замеры —
[bench/README.md](../bench/README.md).

**Счётные кубы.** `with_count=True` (по умолчанию) удваивает память факта.
Если `COUNT(*)` и `AVG` не нужны, отключите:

```python
db.load_csv(..., with_count=False)
```

**Кэш планов** работает автоматически; сбрасывается при загрузке данных.
`db.plan_cache.hits` покажет попадания.

**GPU** включается заменой движка:

```python
from amdb.exec import TorchEngine
db.use_engine(TorchEngine(device="cuda"))
```

Перенос через PCIe окупается только на больших свёртках с высокой
арифметической интенсивностью; `amdb.exec.pick_engine` реализует это правило.
На машине разработчика GPU не было, так что путь написан, но не измерен.

## 11. Границы применимости

Честный список того, где модель не работает или работает иначе, чем ожидается.

**Гранулярность MIN/MAX.** Ячейка куба хранит агрегат по совпадающим
координатам, поэтому `MAX(quantity)` возвращает максимум **по ячейкам**, а не
по исходным строкам. Если ячейка соответствует одной записи — значения
совпадают, иначе это разные величины. Нужен построчный максимум — грузите факт
отдельным кубом с `agg="max"`.

**`COUNT(DISTINCT ...)` не поддерживается** — через свёртку не выражается.
Запрос отклоняется.

**MIN/MAX — редукция, а не свёртка.** Они исполняются вне einsum и не
получают преимущества матричной модели.

**Соединение только по одноимённым измерениям.** `ON a.x = b.y` при `x ≠ y`
отклоняется: в многомерно-матричной модели оси соединяются по имени.

**Комбинаторный взрыв.** Число ячеек — произведение мощностей измерений.
10⁵ клиентов × 10⁴ товаров × 10³ дней = 10¹² ячеек. AMDB — ускоритель плотных
многомерных агрегатов на осях умеренной мощности, а не замена колоночной СУБД
общего назначения. Практический потолок плотного куба — порядка 10⁷–10⁸ ячеек.

**52 индекса на одну операцию einsum.** План с бо́льшим числом различных
измерений автоматически разбивается на цепочку парных свёрток.

**Широкие результаты.** Если запрос возвращает сотни тысяч строк, время уходит
не на свёртку, а на материализацию результата. Преимущество AMDB тем больше,
чем сильнее запрос схлопывает измерения.

## 12. Диагностика ошибок

Все сообщения на русском и указывают, что именно исправить.

| Сообщение | Что делать |
|---|---|
| `неизвестный столбец 'X'; известные измерения: [...]` | Опечатка или измерение не загружено — проверьте `info` |
| `столбец 'X' присутствует в SELECT, но отсутствует в GROUP BY` | Добавьте `X` в `GROUP BY` или заверните в агрегат |
| `GROUP BY по атрибуту 'X' не поддерживается; создайте иерархию` | Атрибуты годятся для `WHERE`, для группировки нужна иерархия |
| `GROUP BY по [...] невозможен: измерения нет ни в одном кубе и нет иерархии` | Куб не содержит эту ось; добавьте иерархию к ней |
| `измерение 'X' категориальное: диапазонные условия неприменимы` | Используйте `IN (...)` или объявите `--ordered X` |
| `условие > 5 неприменимо к атрибуту 'region': значения имеют тип str` | Сравнивайте атрибут со значением его типа |
| `соединение по разным измерениям не определено: оси соединяются по имени` | Приведите имена измерений к общему |
| `деление на меру внутри агрегата не выражается через свёртку` | Замените `SUM(a / b)` на `SUM(a) / SUM(b)` |
| `MAX поддерживается только для одной меры без арифметики` | Это редукция; вынесите арифметику наружу |
| `COUNT(DISTINCT ...) не выражается через свёртку` | Не поддерживается в v1 |
| `промежуточный тензор ... превышает бюджет` | Сократите `GROUP BY` или используйте разреженное хранение |
| `роль 'X' не имеет доступа к измерению 'Y'` | Выдайте грант через `db.grant` |
| `роль 'X' не может агрегировать по измерению 'Y'` | Добавьте `Y` в `GROUP BY` |

Ошибки синтаксиса указывают строку, позицию и подчёркивают проблемное место:

```
ошибка: ожидалось имя, получено 'FROM' (строка 1, позиция 8)
  SELECT FROM sales
         ^
```
